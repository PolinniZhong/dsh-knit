# Git 变更关联 · 真实任务量尺（v1）

> **这一份回答的不是「机制通不通」，而是「值不值」。**
> 机制那一侧已经冻结（`docs/git-aware-context.md`，827/827，净室闸门通过）。这一份只做一件事：
> 用**真实开发历史**量「变更关联牵出来的测试与文档里，有多少是当时真漏了、后来又被补上的」。
>
> 复现：`cd knit && node tools/changes-value-eval.mjs --repo . --limit 40 --lookahead 40 --json /tmp/v.json`
> 单例核查：`node tools/changes-value-eval.mjs --repo . --commit <sha>`

---

## 一、为什么用「后来又被补上」当判据（测试修改）

`git` 里只有事实，没有意图。一次提交没带某个测试，可能是**不知道要改它**，也可能是**知道但这次不改**。
两者在提交那一刻长得一模一样。

能把它区分开的唯一客观证据是**后续提交**：如果后来有人把「那一篇」和「本次改动的某个文件」
**放在同一次提交里**改了，那说明它当时确实已经该改，只是漏了。

所以这个量尺： 

- **不构造语料**（回放真实提交）、**不人工标注**（用历史当答案）、**不调参**；
- 回放时走的就是产品自己的那两段代码（`scan()` + `changesPayload()`），**没有第二套实现**；
- 数字难看就难看 —— 报告里难看的那几个数是本节最主要的产出。

## 二、做法（可复现）

```
① 一个临时克隆（对被测仓库只读；此后所有写都在 /tmp 里）
② checkout <commit>^ → cherry-pick -n <commit>   ⇒ 工作区 = 父提交 + 这次改动（未提交）
③ scan() + changesPayload()                      ⇒ 与面板/接口同一份实现
④ 对每条关联目标 T：
     · T 在本次提交里            → 「已带上」
     · T 不在，且后续一次**聚焦提交**（≤ 4 个文件）把 T 和本次改动的文件一起补了 → **强证据**
     · T 不在，且后续有一次提交**只**改了 T（|L| = 1）                          → **弱证据**
     · 以上都没有                                                              → **无证据**
⑤ reset --hard + clean，下一个提交
```

**为什么必须区分「聚焦提交」**：`release:` 那种一次动 8–19 个文件的提交里，任意两篇都「同框」——
松口径下 40 个提交里能判出 **95 条**「实证漏项」。那不是发现，那是 release 提交灌出来的。
加上「聚焦」之后同一个样本只剩 **1 条**。这条差本身就要印在报告里（见 §三表里的「松口径」一行）。

⚠️ 三条**不许越界**的话，写在前面：
1. 这是**回放**，不是「让开发者真的用一次」。它量的是「当时漏改、后来补上」这个**事后事实**，
   **不等于**「当时提醒他就能省下那次返工」—— 后者要做前向实验（§六）。
2. 语料是**一个仓库**（这个插件自己的历史）。换仓库要显式 `--repo`，**不同仓库的结论不许相加**。
3. 「已带上」那一格**恒为 0**，不是成绩：变更关联**结构上**就把变更文件自己排除在结果之外
   （`exclude = seeds`）。写成一行是为了让读者看到这条性质，不是当成指标。

## 三、结果（40 个非 merge 提交）

| | 数 |
|---|---|
| 回放提交 | 40（其中 36 个牵出了关联） |
| 关联目标合计 | 269（其中**测试/文档** 140） |
| ├─ 已带上 | 0（**结构性恒为 0**，见上） |
| ├─ **强证据：后来被聚焦提交一起补上** | **1** |
| ├─ 弱证据：后来被单篇提交补上 | 13（**不能当值用**，见下） |
| ├─ 无证据 | 126（**既不宣称是值，也不宣称是噪音**） |
| └─（对照）松口径 | 95（被 release 提交灌出来的假数） |

**三个桶必须加起来等于 140**（强 1 + 弱 13 + 无 126）。⚠️ 第一版报告这里写的是 139 ——
那是**加 tier 2 之前**的「候选」数（140 − 1），加了弱证据那一层之后没有回头改。
数字对不上就是错，已改。

**弱证据那 13 条为什么不能当值**：它们几乎全是同一个形状 —— 某个 docs 提交牵出了 `README.md`，
而后来 `94b3cb67`（一次**只**改 README 的提交）动了它。`README.md` 是「被频繁提及的磁铁」，
任何一次对它的独立修改都会把所有历史提交「点亮」。**这条给的是「该去人工看哪几条」，
不是「Knit 挣到了 13 分」。**

**强证据那 1 条**（`fc2729d5 feat(layout)…` ⇒ 当时没改 `README.en.md`，后来在 `0aa2757f` 被一起改）
是唯一自动可判的实证，也仍然需要人工读一眼才能当结论。

## 三·补 跨仓库：把同一个量尺放到**别的真实仓库**上

同一条命令、同一套定义，六个仓库（全部是真实历史，没有一个是为此造的）：

| 仓库 | 语言 | 回放提交 | 关联目标 | 测试/文档 | 强证据 | 弱证据 | 无证据 |
|---|---|---|---|---|---|---|---|
| `knit`（本插件） | md + ts | 40 | 269 | 140 | **1** | 13 | 126 |
| `geo-visibility-diagnosticia-publish` | md + py | 13 | 89 | 85 | 0 | 0 | 85 |
| `geo-visibility-diagnosticia-release` | md + py | 7 | 41 | 37 | 0 | 0 | 37 |
| `GEO可见度诊断师` | md + py | 9 | 51 | 45 | 0 | 2 | 43 |
| `GEO可见度诊断师_v2.0` | md + py + js | 7 | 31 | 26 | 0 | 0 | 26 |
| `deepseek-harness` | ts + md | 6 | 18 | 18 | 0 | 0 | 18 |
| **合计** | | **82** | **499** | **351** | **1** | **15** | **335** |

复现：
```sh
node tools/changes-value-eval.mjs --repo "<任意仓库>" --limit 20 --lookahead 20
```

⚠️ **这张表不许当「六个独立样本」读**：
- 四个 `GEO*` 是**同一个项目的不同快照**（同一作者、同一领域）⇒ 它们其实只算**一到两个**独立样本；
- `deepseek-harness` 的 6 个提交里 **3 个一条关联都没牵出**（一个是 0 文件的 CI 提交、两个只动测试）
  ⇒ 有效样本是 3；
- 所以真正的独立样本量在 **3 个左右**，不是 6。

### 这张表量出来的两件事

**① `imports` 与 `tests` 两条关系**只认 JavaScript / TypeScript 的写法。**在 Python 仓库里它们是全黑的**：

| 证据 | 事实 |
|---|---|
| 四个 GEO 仓库合计 **212** 条关联目标 | `references` + `documents` 为主，**`imports` 0 条、`tests` 0 条** |
| 正则 | `IMPORT_RE` 要求 `import … from '…'` / `require('…')` —— **Python 的 `import x` / `from x import y` 没有引号，一条都不匹配** |
| 测试约定 | `isTestRel` 只认 `x.test.*` / `x.spec.*` —— **`test_x.py` / `x_test.py` 不认** |

⇒ 「Knit 对 Python 项目基本只剩文档互引」这句话有数字支撑。**这不是缺陷报告，是能力边界**：
它决定了变更关联在非 JS/TS 项目上能说什么话。

**② 16 KB 的 `head` 窗口漏掉多少文档提及，**取决于文档有多长** —— 不是一个固定的 79%**：

| 仓库 | md 文档 | 窗口内提及 | 全文提及 | 丢失 |
|---|---|---|---|---|
| `knit`（长文档：CHANGELOG 2488 行、评测报告 1679 行） | 9 | 251 | 1165 | **917（79%）** |
| `geo-…-publish`（短文档） | 36 | 785 | 875 | **90（10%）** |

⇒ 正确的说法是：**窗口固定 16 KB，文档越长丢得越多**。79% 是这个仓库（长文档密集）的数字，
不是普遍数字；把它当普遍数字引用就是错。

### 这张表**没能**回答的事

**335 / 351 是「无证据」，而不是「噪音」。** 这个量尺只能看见「漏了**并且后来被补**」，
看不见「漏了**但从没补**」—— 后者在历史里**一点痕迹都没有**。所以：

> 这个量尺给的是**下界**，而且这个下界很低（351 条里 1 条）。**它不足以判定「值不值」。**
> 它能干的是：把「没有证据」精确地拆成「三种已知的结构性盲区」（语言覆盖、文档窗口、无痕迹），
> 从而说明为什么**必须**改用前向实验（§六）。

## 四、案例研究：**提交自己声明「漏了」的那四次**（最强证据）

历史里有四个提交在 message 里明确写了「漏更 / 补上」。它们是最干净的漏项真源 ——
不是我们判的，是当时的人自己写的：

| 修复提交 | 它自己怎么说的 | 修了哪个文件 | Knit 在那次（应当更的提交）上牵出来了吗 |
|---|---|---|---|
| `94b3cb67` | 「测试数 728 → 778（**v0.23 漏更**）」 | `README.md` | ❌ **没牵出来** |
| `e6253a25` | 「修悬空引用 —— 5 处 §8.x 改指平表本体」 | `AGENTS.md` | ⚠️ 结构上看不见（见下） |
| `dd9cecf0` | 「CHANGELOG **补上** 0.16.0 的发布状态」 | `CHANGELOG.md` | ⚠️ 结构上看不见 |
| `aa239633` | 「CHANGELOG **补上** 0.17.0 的发布状态」 | `CHANGELOG.md` | ⚠️ 结构上看不见 |

**「结构上看不见」是什么意思**：后三次的漏项，是**碰了那个文件、但里面少写了一行**
（`CHANGELOG.md` 明明在那次发布的提交里）。而变更关联只回答「**这次一个字节都没碰**、
但和改动有关的文件有哪些」—— 它**没有 diff 级的理解**，所以这类漏项它**原理上答不了**。
这不是缺陷，是边界：一个文件级关联工具不该宣称能发现「改了一半」。

**第一次（README）是可测的那一类，而且 Knit 没答上来。** 根因查清了，见下一节。

## 五、这一轮量出来的真问题：**文档里 79% 的路径提及不产生任何边**

`v0.23.0` 的发布提交 `e4f5507` 改了 19 个文件（含 `src/host/index.js`、`src/host/semantic.js`…），
却漏了 `README.md` 的测试数。Knit 对这次提交牵出 8 个目标：

```
test/fixture.mjs   src/host/index-store.js   src/host/relations.js   src/host/passage.js
src/host/relevance.js   test/code-context.test.mjs   test/control.test.mjs   test/deep-context.test.mjs
```

**`README.md` 不在里面 —— 而且不是被截断掉的**：把上限开到 999，完整候选是 **34 条**，
`README.md` **一条都不在**（`tools/changes-value-eval.mjs --commit e4f5507` 可复现）。

根因（逐步查证）：

| 步骤 | 事实 |
|---|---|
| `README.md` 里提到 `src/host/index.js` 吗 | **提到**，在**第 366 行** |
| 那为什么没有边 | 关系抽取吃的是 `doc.head`，而它是 **16 KB 窗口**（`HEAD_BYTES`）—— README 的 head 只到**第 188 行** |
| head 窗口里抽到几条 `src/host` 提及 | **1 条**（`knit/src/host/passage.js`，第 45 行），第 366 行那条**根本不在输入里** |
| 影响面 | 工作区 9 篇 md：窗口内提及 **251** 条，整份文件 **1165** 条 ⇒ **917 条（79%）不产生任何边** |
| 最严重的几篇 | `CHANGELOG.md` 丢 346/374、`docs/evaluations/hybrid-retrieval.md` 丢 305/341、`AGENTS.md` 丢 93/142、`README.md` 丢 67/94 |
| 相关性排序受影响吗 | **不受** —— v0.20 已经把 haystack 的窗口取消掉了。**只有关系抽取还吃窗口**（`relations.js` 那一处） |
| 修它的成本（实测） | 9 篇 md 全文抽取 **7.33 ms** vs 窗口抽取 **1.75 ms** ⇒ **+5.6 ms / 次冷算**（语料越大线性增长） |

**这是一条有根因、有影响面、有成本的结论**，也是这一轮量尺真正的产出：
它把「Knit 找得准不准」这个模糊问题，换成了「**文档里五分之四的路径提及根本进不了关系层**」
这个具体缺陷。

⚠️ **本轮没有改它**（冻结 + 它会改变既有关系集合，属于需要明确授权的行为变更）。
建议作为下一轮的**唯一**候选改动，附成本与影响面如上。

## 六、前向协议（真正能回答「值不值」的那个实验）

回放量的是事后事实。要量「提醒有没有用」，只能**前向**做，而且必须由人来做：

1. 接一个**真实的**开发任务（不是为本实验造的）；
2. **先写下你自己的判断**：这次改动你认为会牵动哪些测试 / 文档（写进一条命令的参数），
   **在打开 Knit 之前**；
3. 再打开变更关联那一区，记下它多说了哪些；
4. 收工时回答两个数：**它提到的、我确实该改却没想到的**（真收益）／
   **它提到的、其实无关的**（噪音）。

判据（照着写，别含糊）：

```sh
# ② 先固化你的判断（这一条命令就是「实验前的盲测记录」）
#    真实任务开始时，把「我以为要一起改的文件」写进这里
echo "src/host/index.js test/client.test.mjs" > /tmp/my-预判.txt

# ③ 再做一次真实的变更，然后问 Knit（等价于面板上打开「变更」那一格）
node tools/changes-value-eval.mjs --repo <你的仓库> --commit HEAD   # 或直接在面板上看

# ④ 对账：Knit 牵出来的目标里，哪些不在 /tmp/my-预判.txt 里，而事后证明**确实该改**
```

**这条协议的核心是第 2 步的先后顺序**：先写判断、再看 Knit。反过来做就只能得到「Knit 说得对不对」，
永远得不到「它有没有找到我本来会漏的」。

## 七、这一轮没做什么 / 不知道什么

- **没有改任何产品代码**（`src/` 一行未动）。§五那个缺陷只被**量出来**，没被改。
- **独立样本只有 3 个左右**（见 §三·补）：四个 `GEO*` 是同一项目的不同快照、`deepseek-harness` 的
  有效样本是 3。**六个仓库加起来仍然不足以支撑「值不值」的结论** —— 那需要前向实验。
- **弱证据那 13 条没有逐条人工判读**。它们（连同强证据那 1 条）已写进 `--json` 的输出，
  要变成结论必须有人读一遍。
- ~~`README.en.md` 那条强证据没有回头核对~~ —— **已核实，是真的**（这是六个仓库里唯一一条强证据）：
  · `fc2729d`（布局改版，8 个文件）改了 `README.md`，**漏了它的双语孪生 `README.en.md`**；
  · 后来的 `0aa2757`「docs: README 补「反馈」与「升级」，**修过期测试数**」一次改了
    `README.md` + `README.en.md` 两篇。
  ⇒ 这是一个**双语孪生漏改**的真实案例，也正是变更关联最该抓到的那种。**不是误报。**
- **本量尺不评价排序质量**：变更关联不使用名次（固定吃不分档语料），所以这里量到的
  都与「该不该排在前面」无关。
- **量尺自己修过一个只在新仓库上才暴露的 bug**：根提交没有父提交，`checkout <sha>^` 会直接把
  工具抛死。Knit 自己的近 40 个提交离根很远，从没触发过 —— **换仓库当场就触发了**。
  这条本身也是「必须换语料」的论据。

## 八、顺带修好的一处量尺口径（不是产品代码）

`tools/real-workspace-eval.mjs` 的 `EVAL_ARTIFACTS` 只排「**评测自己的产物**」。
本轮把新增的两个评测产物补进去（`docs/evaluations/git-change-value.md`、`tools/changes-value-eval.mjs`），
并**刻意没有**把 `knit/docs/git-aware-context.md` 算作产物 —— 它是产品规格，理应留在语料里。

⚠️ 即便如此，那份报告里的基线数字（`corpusDocs 182` / `R@5 0.479`）**今天也复现不了**，
而且**不该去凑**：v0.25 的实现自己在工作区里长出了 4 个源码/测试文件
（`src/host/git.js`、`src/host/changes.js`、`test/git-changes.test.mjs`、`test/http-harness.mjs`）。
它们是**被测产品**，不是评测产物 —— 把它们排除掉才是伪造语料。所以：

> 那个 182 是「v0.25 之前的工作区」的快照；今天重跑得到 **187**，差异全部来自 v0.25 自己的新增文件。
> **两个数字之间没有可比较性**，任何「R@5 从 0.479 掉到 0.4375」的说法都是把语料变化读成了检索退化。
