# 图内评论（pin 评论）· 设计记录

> **状态：已发布 v0.26.0**（2026-11-14，提交 `3c90fcd` / tag `v0.26.0`；registry `latest = 0.26.0`）。
> 不随包发布（`docs/` 不在 `package.json` 的 `files` 白名单里）。
>
> 起因（用户原话）：「agent 出一批空间/商品图 → 我在图上看哪里结构不对 → 我描述『G3 那块腿粘一起了』，
> agent 得靠猜。……它发出去的不是截图，是『坐标 + 一句话』。我们要的就是这个闭环，落在 Knit 媒体档里。」
>
> 第三轮改交互（2026-11）：用户指出「为了写一句话先进全屏，会话被盖住、也不知道是哪个会话的附件，
> 路径太长」，要求参考 **Codex 的 Canvas view**：「悬停大图放大了，就在这里直接就能添加评论」，
> 并且「在一级页面、不能盖住会话页面」。
> ⇒ 评论从「全屏查看器里的一个模式」改成 **Knit 面板里的画布**：
> **悬停大图 →「评论」→ 面板画布**。整屏查看器保留，但降级成画布里的「全屏」按钮。
>
> 第四轮补附件（2026-11）：用户指出「只投文本、没把图片带进输入框附件，Agent 不知道是哪张图」。
> ⇒ 发送时把**原图**（不带 pin）作为 `File` 与文本放进**同一个 paste 事件**：
> DSH 输入框会先 intake 文件、再插入文本。图片读不到时如实提示，不假装附件成功。

## 一、长什么样（没有新 tab、没有新一栏；会话永远可见）

```
媒体网格 ──hover──▶ 420px 放大预览（右下「评论」）
                     │ 点击
                     ▼
Knit 面板内画布（会话不动）：
  _demo.png · rel             [退出评论] [全屏] [返回]
  ┌──────────────────────────────────────┐
  │  图片（落 pin / 贴 pin 气泡 / 编辑）    │
  ├──────────────────────────────────────┤
  │  编号 + 摘要 + 删除             [发送]  │
  └──────────────────────────────────────┘
```

- **入口**：媒体卡片悬停 → 放大预览（v0.25 已有）现在多一个「评论」按钮/整块可点；
  这块浮窗的收起有 `HOVER_SHOT_HIDE_MS = 220ms` 的延迟，鼠标能从卡片挪进去点它。
- **落点**：点「评论」→ 面板切成画布（`lightboxDock`），**评论模式直接打开**；
  双击卡片仍是原来的整屏查看器（v0.25 语义不动），画布里点「全屏」也能进同一张图的整屏。
- 评论模式里：图内单击落**草稿 pin**（1..n），**编辑气泡紧贴 pin**（默认右下 14px，
  出屏翻边并夹进画布）；Enter 保存、Esc 取消、空文本不落；点已有 pin 可重编辑/删除；
  底部评论栏列出编号 + 摘要 + 删除 + 发送。
- **发送 = 原图附件 + 文本**：图片从同源 `/knit/api/raw`（或对话图 `/knit/api/attachment`）读成
  `File`，与 §四 的文本放进**同一个合成 paste**；DSH 的 `PASTE_COMMAND` 会 `intakeFiles()` 再插入文本。
  文字里仍保留 `rel` / sha 做可追溯的身份。
- **换图**：画布顶部有 `‹ ›` + `1/N`；**滚轮在画布任意位置都能换**（评论栏除外——那里要滚评论列表），
  不用先「返回」再点下一张。
- **评论栏**：有可见描边 + 浅灰底 + 阴影，发送是品牌色主按钮；空态写「点一下图片上的位置，写下第一条评论」，
  不是只甩一句「还没有评论」。
- pin 是**圆点 + 序号**；不做引线标注块、不做框选/画笔/箭头。

## 二、为什么是「面板画布」，不是全屏、也不是悬停浮层里直接写

参考 Codex 官方现在的图片工作流：expanded viewer 有 **Focused view / Canvas view**，
Canvas 里对一张或多张图 Comment / Multi-select，评论（位置 + 文字）发回**同一个 chat**
（[Image generation | ChatGPT Learn](https://learn.chatgpt.com/docs/image-generation?surface=cli)）。
它是**会话里的一个视图**，不是独立页面。

- Infini 分享包的 viewer 本身也是 `position:fixed; inset:0` 全屏（查过它的 `styles.css`），
  所以「不盖会话」不能照它；它值得抄的是 pin 气泡的翻边逻辑（已抄）。
- Knit 的面板本身就在会话旁边 ⇒ 最像 Codex Canvas 的落点是**面板内的画布视图**：
  不新增 tab、不新增右边栏、不新开第二列，只是 KnitBody 的一个 `lightboxDock` 状态。
- 「悬停浮层里直接写」被否：420px 太窄、浮层本来是瞬时的，写长句/翻边都很勉强；
  悬停浮层只做**入口**，编辑落在面板画布（用户 2026-11 拍板）。

**身份问题**：全屏时看不到会话；面板画布始终在会话标签页里，
顶部还有「图片名 + rel」一行，发送目标（当前会话输入框）就在旁边 —— 不会再不知道是哪个会话的附件。

## 三、坐标：落点、pin、气泡共用同一个「实际绘制矩形」

图片是 `object-fit: contain`，stage 框里含 letterbox 空白，**拿 stage 宽度算百分比会让 pin 整体偏移**。

```
img 元素盒 + naturalWidth/naturalHeight
  → contentRect()          // contain 后真正画出图的那块矩形
  ├→ pctFromPoint()        // 点击点 → 0–100 百分比（保留千分位）
  └→ contentViewportOf()   // 整块矩形（视口坐标）
        ↓ 减去画布表面（.knit-lightbox 根）的视口偏移
     commentBox（相对画布表面）
        ├→ pin / 草稿 pin 的像素位置
        └→ 编辑气泡锚点（再经 commentPopoverBox 翻边 + 夹进画布）
```

- 整屏查看器与面板画布**共用同一个根元素** `.knit-lightbox`（只是 class 多一个 `docked`），
  所以 「表面坐标」一套逻辑两边通用；切换时 `ResizeObserver` / `lightboxDock` 依赖会让它重新量。
- 落点入口只有一个：`commentClickPct(event, imgEl)`，源码守卫钉住它**必须**经过
  `contentRect → pctFromPoint`，且**不许出现 stage**、不许读 `devicePixelRatio`。
- 编辑气泡位置由纯函数 `commentPopoverBox(anchor, size, view)` 决定：默认 pin 右下（gap 14px），
  右边放不下翻左、下面放不下翻上，最后夹进画布（margin 12px）。
- 窗口缩放 / 面板宽度变化 / 滚动：`ResizeObserver`（画布根 + img）+ `resize` + `scroll`（capture）+
  图片 `onLoad` 都会重新量。评论数据只存百分比，与像素无关。

## 四、发送文本（事实标准，刻意不随界面语言变）

```
图像 N：<文件名或 rel>（sha256 <前 12 位，若有>）
1.（x：62.5%，y：31.0%）右腿两条腿粘在一起了，分界要出来
2.（x：41.3%，y：57.4%）陶盆和虎尾兰对不上
```

- **N = 输入框里已有附件数 + 1**（第一张附件就是 `图像 1`，第二张 `图像 2`）—— 见 §四·六。
- 百分比 `toFixed(1)`；文案原样、不截断；一条上限 200 字，超了**提示并留在编辑态**。
- 工作区图没有哈希 ⇒ 只写 `rel`/文件名，**不编造 sha**；对话生成图写附件 sha256 前 12 位。
- 发送只**投递**，不自动发送（合成 paste → document drop → clipboard → 下载）。

## 四·五、发送必须带原图附件（这一轮的重大修正）

只发文字时，agent 拿到的是「文件名 + 坐标」。这**有时**够用：工作区图如果能从 `rel` 找到文件，
agent 可以自己打开；但三种情况会失效：

1. 同名文件（`image.png` 在两个目录里）；
2. 文件被移动/改名，文字里只剩旧名字；
3. **对话里生成的图没有工作区路径**，只有 sha256；12 位前缀不足以让 agent 稳定取到那张图。

Codex Canvas 的做法也是把图随评论一起提交（Codex 甚至把整张图以 base64 写进 session）。
所以这里改成：**发送 = 原图附件 + 文本**。

- 图片取**同源**地址（本机 `/knit/api/*`，不是外网；不违反零网络出口）；
- 读成 `File` 后与 `text/plain` 放进**同一个 paste 事件**（DSH `keymap.ts` 的 PASTE_COMMAND
  会先 `handlers.intakeFiles(files)`、再 `handlers.pasteText(text)`）；
- 附的是**原图，不带 pin**（pin 的坐标已经在文本里；带 pin 的叠加图容易被 agent 当成参考图）；
- 图片读不到（fetch 失败 / 宿主无 File）⇒ 仍投文本，状态栏明确写「图片附件没带上」，
  **不假装附件成功**。
- ⚠️ **不要因为 `input.textContent` 还没更新就补第二次 paste**：Lexical 的文本更新不保证同步，
  真机上补第二次会把同一段文字/图片塞两遍（踩过，见 §十）。

## 四·六、多张图与独立段落（2026-11-15）

用户实测两个问题：① 连续发两张图的评论时，输入框里两段**拼在同一个段落**末尾，看不出谁跟谁；
② 每段都写「图像 1」，但输入框里其实已经有附件一、附件二 —— agent 分不清哪段对应哪张图。

修法：

- **编号跟附件顺序走**：`composerState(doc)` 数 `[data-composer-card]` 里已有的图片附件
  （`img[src^="blob:"]` 或缩略图容器），`图像 N = count + 1`。附件一 = 图像一，附件二 = 图像二。
- **每次发送是独立段落**：投递前读输入框是否已有正文；有就在 payload 前加 `\n\n`
  （空输入框不加，避免第一条就空一行），并先把光标放到末尾（`caretToEnd`），
  不会插进用户正在写的句子中间。
- 仍然**只 dispatch 一次 paste**（文本 + File 同一个事件）；状态栏、附件数、编号都从真实 DOM 读，不靠猜。
- ⚠️ Lexical 的 `pasteText` 会把 `\n` 保留成文本换行（不是真 `<p>`）；视觉上两条之间有空行、
  `innerText` 也是 `\n\n`，对 agent 来说就是两段。**不要为了「真段落」去按 Enter** ——
  那会触发发送。

## 五、身份锚定

| 图从哪来 | anchorId | 发送文本里的身份 |
|---|---|---|
| 工作区文件 | `doc.rel`（如 `sub/G3.png`） | `rel` / 文件名；有 `sha256` 字段时附前 12 位 |
| 对话里生成的图 | 附件 `sha256:<64 hex>`（`doc.attachmentId`，没有路径） | 附件 sha256 前 12 位 |

`commentsByAnchor: { [anchorId]: [{ n, xPct, yPct, text }] }`。**编号连续**在 `normalizeComments` 里保证：
删掉中间一条后剩下的重新从 1 排（不然发送文本会出现 `1. 3. 4.`）。

## 六、落盘策略与代价（P0 不落盘）

- 评论只活在 `KnitBody` 的 React state 里：切图不丢 / 退出画布或全屏不丢 / 本会话内不丢；
  硬刷新、关标签、重启 DSH 就没了。
- 为什么不落盘：落盘要处理「工作区图改名 / 内容被换 / 对话图 sha 被清理 / 跨设备」四类身份失效，
  得配清理与失效提示 —— P1 量级。P0 先验证「位置 + 一句话」闭环本身。
- 守卫：评论那段不许出现 `readPref / writePref / localStorage`，也不许新增 `dsh-knit:comment`；
  `dsh-knit:pack` 老守卫仍绿。**代价明说：刷新即失。**

## 十、这一轮踩到、且值得留给后来者的五件事

1. **HMR 只换 JS 不换页面时，`ensureStyle` 的「有就跳过」会让新 CSS 一条都不生效**（上一轮返工主因，已修 + 守卫）。
2. **编辑气泡不能只按百分比摆**：靠右/靠下会出屏，看起来像「停在图片边上」。`commentPopoverBox` 翻边 + 夹取。
3. **`stage` 加 `position:relative` 会把工具条盖住**：工具条/关闭/缩略图带/评论栏必须显式 `z-index:2`。
4. **悬停大图原来是 `pointer-events:none`**：它只是「看一眼」。现在它要当评论入口，必须变可点，
   且卡片 `mouseleave` 要延迟 220ms 收起 —— 否则鼠标还没走到就被卸载。
5. **画布与整屏必须共用同一份 DOM**（`lightboxContent`）：两份 DOM 会让评论状态、焦点、几何各算一套。
   docked 只加一个 class，换的是定位/底色/工具条，不是逻辑。
6. **`input.textContent` 在 paste 刚返回时可能还没更新**：不要据此再补一次 paste —— 真机上会
   把同一段文字/图片塞两遍。只信 `dispatchEvent` 的返回值（Lexical 会 `preventDefault()` ⇒ 返回 false）。
   投递层因此改成「一个事件、文本 + File 一起」，并删掉了所有二次 paste 的兜底。
7. **评论栏不能靠 `bg-layer-2` 分层**：浅色主题下 `bg-layer-1/2/3` 全是 `#fff`，和画布
   `bg-base` 一样白 ⇒ 用户看到的就是「没有评论栏」。改成 `--knit-active-bg`（panel 内可用）
   回落到官方交互令牌，再加描边/阴影/主按钮，两种主题都有明确边界。

## 十一、测试里钉住的可证伪点

- `contentRect`：三种比例逐值相等；`cover`/`fill` 语义不混；畸形输入 `null` 不抛。
- `pctFromPoint` / `pointFromPct`：互逆；出界夹到 0–100；NaN → `null`。
- `commentPopoverBox`：默认 pin 右下；近右翻左、近下翻上；极端角落/超小画布仍夹在表面内。
- `normalizeComments`：畸形回空、空文本不占位、条数上限、编号连续、**不改入参**。
- `commentLines`：头行 sha 截 12 位、无 sha 不带括号、百分比 1 位小数、200 字整条不截。
- 投递：paste 只 dispatch 一次；失败按序回落；全失败 `ok:false`；**有附件时事件里同时带文本与 File**；
  图片读不到时 `image:false`（状态栏如实提示），仍投文本。
- 画布：hover 入口打开 docked（非模态、无缩略图带）→ 落 pin/写/存 → 切整屏/切回不丢 → 返回回网格。
- 发送：原图被读成 File、与文本在**同一个 paste**；`clipboardData.items[0].getAsFile()` 就是它。
- 守卫：见 §八，10 条突变全部证伪过。
