### 🔴 顺手抓到的真缺陷：「全部」档的媒体区会被 40 条窗口挤掉（当时数据下必然发生）

2026-09-29 那版 `screenshot-all.png` 里**只有文档区、没有媒体区** —— 这不是排版问题：

1. 宿主 `src/host/index.js:611` 的 `kind === 'all'` 分支把文档与媒体拼成一个池子：
   `pool = collected.docs.concat(collected.media).sort((a, b) => b.mtimeMs - a.mtimeMs)`；
2. 客户端 `src/client/client.js:1645` 却固定请求 `…&limit=40…`；
3. 实测（2026-09-29）`/knit/api/recent?kind=all&limit=40` → `total: 59`，但 `docs[]` **40 条、媒体 0 条**；
   改成 `limit=100` 才有媒体，而且媒体排在**第 50–58 位**（2026-10-05 同一接口量到媒体在 **26–29 位**）；
4. 于是 `src/client/client.js:1694-1695` 的 `visibleDocs.filter(isMedia)` 恒为空
   （`ALL_DOC_CAP = 4`），媒体区整个不渲染。

**条件是「媒体按相关性掉到第 40 名之外」**：`kind=all` 时客户端只取一个 40 条的窗口，
文档够多、媒体又排得靠后时媒体会被整体截掉，而 `mediaItems` 只从这个窗口里筛，
于是媒体区整个不渲染（`ALL_DOC_CAP = 4` 只截文档、不截媒体）。
**2026-10-05 实测：同一接口在更新后的数据里媒体排在 26–29 位，媒体区正常出现** ——
所以不是「永远不出现」，是「取决于排名」。图注按当期实测写。
**本轮不修**（0.13 系列遗留）；要修的最小改法是让 `kind=all` 走两段取数，
或者把窗口按 `docs + media` 的总数放大（需要先确认性能）。

### 🔴 录这条动图时发现的两件事（都写进了图注与工具里）

1. **重排不是瞬时的，正确说法是「0–5 秒」。** 面板是**每 5 秒轮询一次**（`POLL_MS`，
   见 `src/client/client.js`），所以重排在发消息之后的 0–5 秒内落到哪一帧全看运气。
   实测两次：一次 2.9 秒、一次 2.3 秒。
   ⚠️ **发布规划 §4.4 与旧图注里那句「让列表在 1 秒内重排」是不准的** —— 已改掉。
   动图按 10 fps 编码、比真实时间快（这是一般动图的惯例，但图注里要说明）。
2. **面板列表被滚动过就拍不出重点**：重排看的就是「顶上那几篇换了没有」，
   如果列表停在半截，画面上看不出变化。录之前把 `scrollTop` 归零。
