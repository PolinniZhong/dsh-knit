# 媒体收藏 · 设计记录

> **状态：已实现、未发布**（未提交、未进 CHANGELOG、未发版；L0 §1 已如实记为「未提交」）。
> 这份不随包发布（`docs/` 不在 `package.json` 的 `files` 白名单里）。
>
> 起因（用户原话）：「媒体模块，选中图片增加一个收藏，收藏就要默认在媒体列表第一行出现，以此类推」。

## 一、长什么样

- **收藏入口在媒体预览头**：打开一张图 / 一个视频 → 头里多一个 `[收藏]` / `[已收藏]` 按钮（二态，点一下就切换）。
  **只在媒体档出现** —— 文档 / 代码上没有这个按钮（理由见 §三）。
- **收藏的排在网格最前面**，名字行前面多一个 `★`（状态标记，解释「这张为什么在第一格」）。
- 再点一次＝取消；取消到空**不留垃圾键**。

## 二、顺序规则：**稳定分区**，不是第二套排序

```
收藏的（按原有顺序）  ++  其余的（按原有顺序）
```

「原有顺序」＝当前「相关 / 最新」排出来的那一份。所以：
- 收藏**内部**谁在前仍由排序决定 —— 它**没有**变成第三种排序口径；
- 没有收藏时 `orderFavorites()` **原样返回同一个数组**（同一引用，省一次无意义的重渲染）。

这条是刻意的。做「按收藏时间排」「按名字排」都会让用户面对第三种「为什么是这个顺序」，
而排序本身已经是产品的答案（L1 §7.3：不做相关度可视化）。

## 三、为什么不复用既有的「固定 / 排除」

- 那一套（`control.pin` / `control.exclude`，宿主存储 `knit_control`）服务的是**三层 Context Pack**；
  **媒体不参与那个包**（§7.2），媒体卡片上也从来没有那个入口。
- 「固定」的语义是**移出三层、进一个独立的固定区**；「收藏」的语义是**留在本列表里、排到最前**。
  两者不是同一件事，硬合并会把两个概念都弄糊。

## 四、落盘：localStorage，按工作区隔离

- 键 `dsh-knit:favorites`，值 `{ "<工作区根>": ["a.png", "b.mp4"] }`
  —— 走既有的 `readPref / writePref`（L1 §6.4：这一族只放**语义偏好**，收藏属于此类，不是界面几何）。
- **按工作区根分格**：换项目不会串；最多记 `FAV_MAX_ROOTS = 5` 个工作区、每个最多 `FAV_MAX_RELS = 200` 条
  （当前这个工作区**永远保留**）。
- **畸形值一律回空表、不抛**：`parseFavorites()` 要能吃下「上个版本写的」「手改坏的」「别的插件写坏的」。
- **代价明说**：localStorage 只在这台机器的这个 App/浏览器里 —— **不跨设备同步**。
  要跨设备就得走宿主存储（`knit_control` 那套），那是另一个量级的改动（宿主 + 接口 + 重启 DSH），本次没做。

## 五、取证

| 层面 | 手段 | 结果 |
|---|---|---|
| 纯函数（落盘解析 / 取一格 / 加取消 / 稳定分区） | **6 条真断言** | 全绿：畸形值不抛、不改入参、两组内部保序、空收藏原样返回同一引用 |
| 渲染（收藏排最前 + `★` + 头部二态按钮 + 落盘/撤回） | 替身里真跑组件 | 全绿：顺序 `['demo.mp4','a.png']`、★ 只有一个、`收藏 → 已收藏 → 收藏`、取消后不留空键 |

## 六、这一版踩到的两件事（留给后来者）

1. **`const body = …` 在组件中间就求值了** ⇒ 读「末尾才声明的 state」会 TDZ
   （`Cannot access 'favoriteSet' before initialization`）。修法：把列表体包成 `listBody()` 在 return 里调用一次。
   教训：**新状态追加到末尾**（替身按下标 seed 钩子）之后，「中间算出来的常量」不能再直接读它。
2. **effect 依赖 `state.root`，而根是异步到手的** ⇒ 测试里 `render → flush → render` 之后必须**再 flush 一次**，
   否则那条 effect 根本没跑（假绿：以为测了加载，其实测的是空数组）。
