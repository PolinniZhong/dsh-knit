# 对话里生成的图 · 设计记录

> **状态：已实现、未发布**（未提交、未进 CHANGELOG、未发版；L0 §1 已如实记为「未提交」）。
> 不随包发布（`docs/` 不在 `package.json` 的 `files` 白名单里）。
>
> 起因（用户原话）：「现在我发现一个新功能啊，就是在对话中生成的图没有保存到本地，我们的 knit 这个媒体中
> 没有办法拿取，这个可以开发成一个功能吗？就拿到本地以后就不重复出现，但不拿在对话中就要出现在
> 我们 knit 的媒体中」。

## 一、前提（先核实过，不是猜）

在对话里生成的图**不在工作区里** —— 它们落在 DSH 的附件库：
`<dsh home>/attachments/v1/objects/<sha256 前两位>/<sha256>`（`-r--------`，内容寻址）。
Knit 的扫描只能看会话工作区内，所以那些图在媒体档里一个都看不到 —— 与用户观察一致。

## 二、数据从哪来：**会话事件，零 I/O**

会话事件里图的元数据本来就是全的（实测一条真的）：

```json
"type":"image","attachment":{"attachmentId":"sha256:d33f4f2a…","mediaType":"image/jpeg",
  "width":1072,"height":649,"bytes":39490,"name":"image.png"}
```

而且**「工具产出的」与「用户贴的」是结构上分开的**（实测同一个会话的事件统计）：

| 事件 | 位置 | 样本 |
|---|---|---|
| `tool/result` ← **生成的图（本功能收录的）** | `data.message.content[]` | `D1_健身房握哑铃_v0.1.png`、`双色戒指-产品图精修-定稿.png` |
| `user/message` / `agent/inbox/spliced` ← **用户贴的图（不收）** | `data.content[]` / `data.inserted[].content[]` | `image.png`、`image29.png`、`参数表.jpg` |

⇒ 「本会话有哪些图」这件事**不需要读盘**：`attachmentsFromEvent()` 是一次纯函数。

## 三、边界：这是全插件**唯一**读工作区之外的地方

新增两条路由（宿主半边 ⇒ **改了要重启 DSH**）：

```
GET /knit/api/attachments?sessionId=…             → 本会话工具产出的图（已去掉「本地已有」的）
GET /knit/api/attachment?sessionId=…&id=sha256:…  → 那一个对象的字节
```

**三条边界，缺一不可**（每条都有 e2e + 突变证伪）：

1. **只认 `sha256:<64 hex>`，不接受任何路径**。路径由 `objectPath()` 用哈希算出来
   （前两位做目录）—— 不是「过滤 `..`」，而是**根本没有接受路径的入口**。
2. **id 必须在本会话的 `tool/result` 里出现过**（`createAttachmentStore.has()`）。
   跨会话、没出现过、用户自己贴的图 —— 一律 `404`。
   ⚠️ **回填也必须校验「请求里的 sessionId」与「解析出的会话 id」一致**
   （`session.id !== sessionId` 就跳过），否则伪造一个 id 只要解析到任意会话，
   就能把那个会话的图登记到伪造 id 名下 —— 等于绕过这条闸门。这条是**证伪时发现并补上的**。
3. **只回 `image/*` / `video/*`**，走既有的 `sendMedia`（`nosniff` + `default-src 'none'; sandbox`），
   `Content-Type` 取**事件里的 `mediaType`** —— 附件对象**没有扩展名**，不能按后缀判。

## 四、去重：**按内容（sha256）**，不是按文件名

你存成什么名字都行，只要字节一样就不会重复出现。代价刻意压到最低：

```
候选 = 媒体档扫描结果的 {rel, size}
嫌疑 = 候选里 size 与某条附件 bytes 相同的（大小不同绝不可能同内容）
哈希 = 只给「嫌疑」算 sha256  ← 不扫全库、不给每张图算哈希
```

⚠️ 两个实现细节（都是踩出来的）：

- **候选不能用 `contextCorpus`**：那是「文档 + 代码」那一份，**媒体从不在里面**（媒体不参与 Context Pack）。
  也不能用 `kind: 'context'` 的 `allDocs` —— 实测那样连一张图都没有。必须用 `kind: 'media'` 扫一遍。
- 扫描结果有 **8 秒备忘**：把图存进工作区之后，**下一次扫描**才看得见（与面板 5 秒轮询同窗）。
  所以「存进去 → 它消失」有最多约 8 秒延迟，这是**设计如此**，不是卡住。

## 五、UI

- 媒体档里**和文件混排**，顺序：**收藏 → 对话里生成的（新的在前）→ 其余**。
  （收藏仍然排最前 —— 那条规则没变，只是把「还没存进项目的图」插在收藏之后。）
- 带一个**文字标记「对话」**（不是图标：它承担信息 —— 还没存进项目、存进去就消失），
  悬停提示写「对话里生成的图，还没保存到本地」。
- 点开就地预览（走同一条网格 / 预览 / 键盘路径）；`本地打开` 这类按钮因为它没有工作区路径而置灰。
- **只在媒体档取数**（`kind === 'media'` 才发那次请求）；接口失败 / 老宿主没有这条路由 ⇒ 静默降级成「只显示文件」。

## 六、取证

| 层面 | 手段 | 结果 |
|---|---|---|
| 纯函数（id 校验 / 事件抽取 / 登记簿 / 去重） | **6 条真断言**（`test/attachments.test.mjs`） | 全绿：`../` 一律算不出路径；`user/message` **即便信封与 `tool/result` 同形**也不收；登记簿跨会话不认、有界（每会话 200 / 24 会话 LRU）；去重只给同尺寸候选算哈希 |
| **真实回环端口 e2e** | **6 条**：列表 / 去重 / 回字节 / 跨会话 / 用户贴图 / 对象缺失 | 全绿：`content-type` 来自事件（`image/png`）、`nosniff` + `sandbox` 都在、字节逐字相同 |
| 客户端接线 | **3 条**（顺序 + 标记 + `src` 走附件路由 / 文档档不取数 / 接口失败静默） | 全绿；并断言**文件图仍走 `/api/raw`**（既有路径没改） |
| **守卫是否空转** | **6 条突变逐条证伪** | **6/6 如期变红**：去掉去重 / 去掉会话 id 校验 / 去掉 `tool/result` 收窄 / 放宽类型 / 对话图改回 `raw` / 去掉「对话」标记 |

⚠️ **真人真机验收还没做**：要在真面板上「生成一张图 → 媒体档看到它 → 存进项目 → 它消失」走一遍，
以及**重启 DSH 之后历史图还在**（靠回填）。判据照 `03_发布/真机验收清单.md`。

## 七、一处**需要你知道的偏离**

回填要读会话已有事件，用的是 `session.snapshotEvents()` —— 而 L1 §6.11 写着它
「已被 DSH 标 deprecated，**不许新增生产调用**」（当时只有两处：`rankByRelevance` 当检索输入、
v0.17 的 `backfillFeedback`）。**本功能是第 3 处。**

- 为什么非要它：只靠订阅的话，**插件启动之前**生成的图一条都收不到 —— 用户看到的是永远空着的列表
  （重启前的历史全没了），等于没做。
- 照抄 v0.17 那条例外的三条边界：**一个会话只做一次**（`attachmentBackfilled`）、
  **同步零 I/O**（只在内存里过一遍事件）、**失败一律吞掉**。
- 不这么做的话，替代方案只有「读 DSH 的会话日志文件」（`session.v4.jsonl.zstd`）——
  那是**更糟**的一条路：又多一处读内部文件的地方，还依赖压缩格式与文件名。
- **发版时应当在 L1 §6.11 补一句**（把例外从「1 处」改成「3 处」）。

## 八、明确**没做**的

- **「保存到本地」**：那要一条**写**路由（Knit 会往你的项目里写文件）—— 产品定位级变化，
  本次没做。手动存一份，同一条去重规则照样生效。
- **用户自己贴的图**：默认不进媒体档（隐私更保守）。要的话可以加开关，但默认不。
- **跨设备同步**：列表来自会话事件、字节来自本机附件库 —— 换机器就看不到（本来也不该看到）。
- **已发送 > 12 MB 的图**：既不列也不读（与图片上限同档）；`video` 也按 12 MB 这一档，
  比 `/api/raw` 的 256 MB 视频上限更保守 —— **宁可不显示，也不去搬大文件**。
