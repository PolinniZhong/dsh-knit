# 预览里的查找（Cmd+F）· 设计记录

> **状态：已实现、未发布**（未提交、未进 CHANGELOG、未发版；L0 §1 已如实记为「未提交」）。
> 规格与取证都在这一份里 —— 它**不随包发布**（`docs/` 不在 `package.json` 的 `files` 白名单里）。
>
> 起因（用户原话）：「文档详情阅读时，想加入一个"Command+R" 是可以进行搜索文档，像谷歌浏览器那样
> "Command+R" 搜索关键词定位」。

## 一、先纠正了键位

**Chrome 的「查找」是 `Command+F`；`Command+R` 是「重新加载页面」。**
而本项目的开发流程里 `Cmd + Shift + R` 正是用来硬刷新客户端半边的（L1 §6.5）——
把 `Cmd+R` 占掉会顶掉一个正在用的键。所以实现的是 **`Cmd+F`**（与 Chrome 的查找一致），
并已向用户说明；要改键是一行的事（`onRootKeyDownCapture` 里那个判断）。

## 二、长什么样

- 预览面板里，**头与正文之间**多一行查找条（位置与既有的引用条 `.knit-links` 同一层）。
- 组成：输入框（复用工具栏那套 `.knit-searchwrap` + `.knit-filter` 的观感）→ 计数 `3/12` → `↑` `↓` → `✕`。
- 打开时输入框自动聚焦；`Enter` 下一个 / `Shift+Enter` 上一个（环绕）；`Esc` 关掉查找条。
- 媒体档（图片 / 视频）没有可搜的正文 ⇒ **不打开**，快捷键交回宿主 / 浏览器。

## 二·补、**还要有一个按钮**（2026-10-15 实测之后加的）

**用户实测：按 `Cmd+F` 出来的是外层应用自己的查找框** —— 一个和本功能无关的 `0/0` 窗口。

⚠️ **归因改过一次，两次都记在这里**（最初写成「飞书客户端的内置浏览器」，错）：
真身是 **DSH 官方桌面 App 自己的页内查找** —— 证据是 `app.asar` 里有 `find-in-page` ×6、`FindBar` ×2。
而「DSH 没绑 Cmd+F」这个第一版结论来自一条**静默失败的命令**（`cd` 进了一个不存在的路径
`app.asar/dsh`，之后的 grep 全打在空气上，我把空白输出读成了否定结论）——
**「没有检查」和「检查过了」长得一模一样**，这次是活证据。

原因不在本功能的代码：**App 级快捷键在按键进入网页之前/之外就被处理掉了**，
网页侧（`preventDefault` / 捕获阶段）**抢不回来**。任何只看网页的写法都赢不了这一层。
顺带一句：App 那个查找**本身是可用的**（它搜整个页面，包含预览区），
它缺的是「只在本篇文档内计数 + 逐个定位」。

⇒ 所以预览头多了一个 **「查找」按钮**（`!isMedia` 才出现，媒体档不留死按钮）：
**能力必须有一个不依赖快捷键的入口**。快捷键是加分项，不是唯一入口。
⚠️ 这条改变与预览头原有那四个按钮（网页预览 / 本地打开 / 全屏 / ✕）是**并列关系**，
没有删改任何一个 —— 但「预览头的按钮集合」这件事从此变了，已向用户报告。

另外两件与它相关的事实（下次排查先看这两条，别再从代码找）：

1. `Cmd+F` 只在**已经打开一篇非媒体预览**时才接管（没有可搜的正文时故意让给宿主 / 浏览器）。
   所以「没打开文档就按 Cmd+F」本来就会看到外层那个查找框 —— 那是**设计如此**，不是坏了。
2. 快捷键挂在**面板根**上 ⇒ 焦点必须在 Knit 面板里。焦点在中间对话区时收不到。

## 三、三条硬约束（都是既有房规，不是新定的）

1. **不自己渲染 Markdown**。`DocPane` 那条注释写得很清楚：自己渲染就成了第二套渲染器，会与 DSH 的
   主题、代码块复制、相对图片解析全部脱钩。所以走**与 `docAnchorHit` 同一套办法** ——
   渲染完成后用 `TreeWalker` 在**已经渲染出来的文本**上找，找到就包 `mark`。
2. **命中只上底色，绝不动几何**。`mark.knit-find` 里 `padding:0`、`border:0`、`color:inherit`
   （不 inherit 的话浏览器默认的 `mark` 是黄底黑字）。代码预览的命中横带是按
   「滚动高度 ÷ 行数」算行高的，命中一旦有内边距或边框，横带就错位。
3. **两级灰阶建立层级，不引入第二种颜色**：普通命中 = `--knit-hover-bg`（三档里最弱），
   当前命中 = `--knit-chip-bg`（最强，与命中段同源）。

## 四、两条已知边界（明说，不藏）

1. **命中不跨文本节点**。渲染会把 `**粗**字` 拆成两个节点，所以**正好被 Markdown 语法截断的关键词**
   （一半在「粗」左边、一半在右边）找不到。与既有锚点定位是同一条边界。
   跨节点要额外把「归一化后的下标」分别映射回两个节点的原文下标，代价与收益不成比例。
2. **`preview.truncated` 那句「仅预览前 512 KB」不算文档内容** ⇒ 不搜它（跳过 `.knit-preview-note` 子树）。
   大文件被截断时，查找只在**显示出来的那一段**里找 —— 计数反映的就是这个，不假装搜过全篇。

## 五、为什么状态在 `KnitBody` 而不是 `PreviewPanel`

快捷键挂在**面板根**上，而且是**捕获阶段**（`onKeyDownCapture`）：

- **必须在根上**：焦点通常在左边那个列表上（`↑↓` 打开预览），挂在 `.knit-preview` 上根本收不到
  那个事件 —— 事件从列表冒泡，不经过预览。
- **必须在捕获阶段**：列表自己有 `Esc`（退全屏 / 关预览）。查找开着时 `Esc` 的语义应当是
  **先关查找条**，捕获先于子节点执行，`stopPropagation()` 就把它拦下了。**一次只吃一层。**
